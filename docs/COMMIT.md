# 학교생활 커밋 규칙

복잡한 브랜치 전략 없이 `main` 브랜치에 바로 push한다.

목표는 새 기능을 많이 넣는 것이 아니라, 데모가 깨지지 않는 상태로 빠르게 제출하는 것이다.

## 지금부터 원칙

- `main` 브랜치에서 작업하고 바로 push한다.
- push 전에는 반드시 로컬 실행 또는 핵심 화면 동작을 확인한다.
- 큰 기능 추가보다 데모 플로우 완성을 우선한다.
- 같은 파일을 수정할 때는 팀 채팅에 먼저 공유한다.
- 15~20분 이상 막히면 바로 팀에 도움을 요청한다.
- 발표 직전에는 치명적인 버그 수정, 문서 정리, 배포 확인만 한다.

## 작업 순서

1. `README.md`, `docs/*.md`, `BUILD_LOG.md`를 빠르게 확인한다.
2. 지금 맡은 작업을 팀 채팅에 짧게 공유한다.
3. `main`에서 바로 작업한다.
4. 로컬 실행 또는 핵심 화면을 확인한다.
5. 커밋 후 바로 push한다.
6. push한 내용을 팀 채팅에 공유한다.

```bash
git checkout main
git pull origin main

# 작업 후
git status
git add .
git commit -m "type: 작업 내용"
git push origin main
```

## Commit Message

커밋 메시지는 아래 형식을 사용한다.

```txt
type: 작업 내용
```

예시:

```txt
feat: 메인 페이지 추가
fix: 로그인 버튼 오류 수정
docs: 실행 방법 추가
style: 메인 화면 간격 조정
chore: 배포 설정 수정
```

자주 쓰는 type:

| Type | 의미 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `style` | UI 스타일 수정 |
| `chore` | 설정, 패키지, 빌드 작업 |

## Push 전 체크

- [ ] 최신 `main`을 pull 했다.
- [ ] 내가 수정한 파일을 확인했다.
- [ ] 로컬 실행 또는 핵심 화면을 확인했다.
- [ ] 불필요한 로그, 테스트 코드, 임시 파일을 제거했다.
- [ ] 팀 채팅에 push 내용을 공유할 준비가 됐다.

## Push 후 공유 예시

```txt
[push] main 업데이트 완료
- 작업 내용: 메인 페이지 UI 수정
- 확인 내용: 로컬 실행 확인
- 남은 일: API 연결 확인 필요
```

## 충돌이 생기면

- 혼자 오래 해결하지 말고 바로 팀에 공유한다.
- 충돌난 파일을 마지막으로 수정한 사람과 같이 확인한다.
- 해결 후 다시 실행 확인을 하고 push한다.

## 발표 전 체크

- [ ] 핵심 데모 플로우가 처음부터 끝까지 동작한다.
- [ ] 배포 주소가 정상 접속된다.
- [ ] 발표용 계정 또는 더미 데이터가 준비되어 있다.
- [ ] 실패했을 때 보여줄 백업 화면이나 캡처가 있다.
- [ ] 발표자가 데모 순서를 최소 1번 이상 리허설했다.

## 마지막 작업 로그

작업 중 중요한 결정이나 문제는 `BUILD_LOG.md`에 짧게 남긴다.

```txt
[시간] 작업 내용 / 문제 / 해결 방법 / 남은 일
```
